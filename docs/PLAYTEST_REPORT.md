# 플레이테스트 보고서 — 승급의 계단 PoC (1~20층)

작성일: 2026-11-18 · 대상: `demo/`(재생 모드 버전), `demo_api/`(Claude API 버전) · 테스트: Claude Code

## 한 줄 요약

처음 빌드는 **하트가 너무 빨리 바닥나는** 게임이었습니다(숙련자 유형도 5판 중 1판만 승급). **새 층마다 하트 1 회복**을 넣은 뒤 숙련자·보통 유형은 대부분 승급하고, 직접 전체화면으로 플레이해도 두 버전 모두 20층 승급까지 갈 수 있었습니다. 플레이 중 찾은 **문구 겹침**과 **게임 안 조작법 부재**도 고쳤습니다.

## 1. 테스트 방법

| 방법 | 내용 | 한계 |
|---|---|---|
| A. 유형별 실시간 자동 플레이 | Playwright로 실제 키를 누르는 스크립트. 숙련자·보통·초보 3가지 유형으로 유형마다 5판 | 유형의 수치는 가정값이라 실제 사람의 승률이 아님. 경향 확인용 |
| B. 명세 시뮬레이션 | Mechanics 에이전트의 `mechanics.json`(1~100층) 수치로 판정만 계산, 유형마다 300판 | 실제 게임 코드가 아님. 21층 이후는 아직 빌드가 없음 |
| C. 전체화면 직접 플레이 | 앱 내 브라우저를 1920×1080(6배 확대)으로 띄우고 화면을 보며 직접 조작 | 조작 지연 때문에 "일시정지로 읽기 → 짧게 재개해 몇 칸 오르기"를 반복. 일시정지 중에는 남은 일수와 공격도 멈추므로 규칙은 그대로이나 패링 타이밍은 추정 |

방법 A의 플레이어 유형:

| 유형 | 초당 계단 | 방향 실수 | 패링 타이밍 오차(표준편차) | 패링 놓침 |
|---|---|---|---|---|
| 숙련자 | 6.0 | 2% | 50ms | 3% |
| 보통 | 4.5 | 4% | 80ms | 8% |
| 초보 | 3.5 | 7% | 120ms | 15% |

## 2. 결과

### 2-1. 하트 회복 전후 (방법 A, 20층 승급 판 수 / 5판)

| 버전 | 유형 | 회복 전 | 회복 후 | 회복 후 도달 층 |
|---|---|---|---|---|
| demo | 숙련자 | 1/5 | **5/5** | 모두 20층 |
| demo | 보통 | 0/5 | **5/5** | 모두 20층 |
| demo | 초보 | 0/5 | 1/5 (Mechanics 병합 뒤 재측정 0/5) | 2~20층 |
| demo_api | 숙련자 | 1/5 | **5/5** | 모두 20층 |
| demo_api | 보통 | 0/5 | **3/5** | 12~20층 |
| demo_api | 초보 | 0/5 | 0/5 | 2~14층 (평균 3.4층 → 8.2층) |
| 내장 봇 `?bot=1` | — | 승급 | 승급 | demo 약 14초, demo_api 약 22초, 하트 3개 |

- **패배 원인은 모두 하트 소진**이었습니다. 남은 일수는 가장 낮을 때도 20일 이상이라, 일수가 바닥나서 진 판은 없었습니다.
- **입력 처리는 정상**입니다. 잘못 밟아서 맞은 횟수가 스크립트가 일부러 낸 실수 횟수와 매 판 정확히 같았습니다.
- demo_api가 더 어려운 이유: 한 층이 6칸이라 승급까지 114칸(demo는 95칸)이고, 20층 근처 공격 간격이 1.1초(demo는 1.3초)입니다.

### 2-2. 1~100층 명세 시뮬레이션 (방법 B, 유형마다 300판)

| 조건 | 유형 | 20층 | 40층 | 60층(노말 엔딩) | 100층(CEO) |
|---|---|---|---|---|---|
| 층마다 회복 O (현재 명세) | 숙련자 | 98% | 95% | 92% | 87% |
| | 보통 | 73% | 51% | 34% | 11% |
| | 초보 | 16% | 1% | 0% | 0% |
| 층마다 회복 X | 숙련자 | 39% | 10% | 1% | 0% |
| | 보통·초보 | 0% | 0% | 0% | 0% |

- 61층부터 시작하면(하드 구간만) 숙련자 94%, 보통 38%, 초보 0%가 CEO에 도달했고, 초보는 일부 판(5%)에서 **남은 일수가 바닥**났습니다. 99층은 패링을 다 막아도 초당 약 3.5칸이 필요합니다(명세의 계산과 일치).
- 결재판 좌우 동시(Q+E), 전화기 고속 비행은 이 모델로 체감 난도를 판단할 수 없습니다. 사람이 직접 해 봐야 합니다.

### 2-3. 전체화면 직접 플레이 (방법 C)

| 회차 | 버전 | 결과 | 계단 실수 | 피격 / 패링 성공 | 메모 |
|---|---|---|---|---|---|
| 1 | demo | 7층 구조조정 (34칸) | 2 | 1 / 0 | 계단을 잘못 읽고, 패링이 판정보다 약간 이름 |
| 2 | demo | **20층 승급**, 하트 3, 1,100점 | 0 | 2 / 4 | 하트 1·남은 일수 7일까지 몰렸다가 9·10층 회복으로 회생 |
| 3 | demo_api | 1칸에서 중단 | — | — | 앱 내 브라우저가 페이지를 "숨김"으로 보고해 자동 일시정지가 반복됨(환경 문제) |
| 4 | demo (문구 수정 후) | **20층 승급**, 하트 3, 1,000점 | 0 | 4 / 1 | 첫 판 승급 |
| 5 | demo_api (문구 수정 후) | 16층 구조조정 (93/114칸), 2,480점 | 0 | 6 / 1 (무인 상태 2회 포함) | 자동 일시정지 뒤 제 ESC가 게임을 재개시켜 무인 상태로 피격(조작 문제) |
| 6 | demo_api | **20층 승급**, 하트 3, 3,190점 | 0 | 3 / 3 | 정지 전에 진행 상태를 확인하도록 바꾼 뒤 첫 판 승급 |

- 6배 확대에서도 픽셀이 깨지지 않고 계단, HUD, 키 아이콘, 결과 화면이 또렷합니다.
- 계단 옆 **층 표시(2F, 3F…)가 길 읽기의 기준점**으로 매우 유용했습니다.
- 19층 근처에서 다음 구간의 색이 다른 계단이 미리 보여 "곧 승급"이라는 기대감이 생깁니다.
- 14층 이후에는 거의 한 번 오를 때마다 공격이 하나씩 들어와, **층마다 하트를 잃고 되찾는** 흐름이 됩니다.
- demo_api는 층 보너스(100점) 때문에 같은 층이어도 점수가 demo의 2~3배라, 두 버전의 점수를 바로 비교할 수 없습니다.

## 3. 플레이테스트로 고친 것

| 문제 | 수정 | 커밋 |
|---|---|---|
| 하트가 3개뿐이고 회복이 없어 실수 몇 번에 판이 끝남 | 새 층마다 하트 1 회복(최대 3). demo `CONFIG.FLOOR_HEAL`, demo_api `CONFIG.floorHeal`, Developer 지시문에도 반영 | `652b8d3`, `05a7cbb` |
| 게임 안에서 조작법을 볼 곳이 없음 | 타이틀·일시정지에 "조작법" 화면 추가(ESC로 닫기, 열려 있는 동안 남은 일수 정지). `HOWTOPLAY.txt` 추가 | `c274d4f`, `115a69e` |
| "하트 +1"과 "막았다!"가 겹쳐 "하트 +막았다!"로 보이고, 회복 문구끼리 쌓임 | demo: 문구를 두 줄로 나누고 같은 줄은 덮어씀. demo_api: "7F · 하트 +1"로 한 줄 합침 | `c5c8847` |

모든 수정 뒤 두 재생 모드의 Publisher 동작 확인 9개 항목이 통과했습니다.

## 4. 남은 문제와 제안

1. **하드 구간 난이도 (기획 판단 필요)**: 층마다 회복이 있으면 숙련자는 87%가 CEO까지 가고, 없으면 60층 도달도 1% 수준입니다. 몇 층마다 회복, 구간이 오를수록 회복량 감소 같은 중간값이 필요해 보입니다. (명세 보고서의 플레이테스트 질문 4번)
2. **초보 유형은 여전히 어렵습니다**: 1~20층에서도 승급이 0~1/5입니다. 주된 원인은 계단 방향 실수이므로, 실수 1회의 벌칙을 하트 대신 남은 일수 감소로 바꾸는 방안을 검토할 만합니다.
3. **demo_api 전체화면 버튼**: 앱 내 브라우저에서 눌러도 반응이 없었고, 실패해도 안내가 나오지 않습니다. 일반 Chrome에서는 아직 확인하지 않았습니다.
4. **demo_api의 경쟁 사원 장식**: 계단 위를 지나다니지만 공격하지 않는 장식이라, 처음 보는 사람은 피해야 하는 대상으로 오해할 수 있습니다. 1~20층에서는 흐리게 그리거나 배경 쪽에 두는 것을 제안합니다.
5. **패링 판정이 빡빡합니다**: 직접 플레이에서 성공률이 높지 않았습니다(타이밍 추정의 한계도 있음). 사람 대상 테스트로 0.20초 판정이 적당한지 확인이 필요합니다.
6. **21층 이후는 빌드가 없습니다**: Mechanics 명세를 반영한 게임은 API로 다시 생성해야 나옵니다(`python -m stairs_agents run --record`).

## 5. 다시 해 보려면

```bash
python -m stairs_agents run --replay replay                              # demo 빌드 + 동작 확인 9개
python -m stairs_agents run --replay replay_api --out output_api        # demo_api 빌드 + 동작 확인 9개
```

- 게임: `demo/index.html`, `demo_api/index.html`을 브라우저로 엽니다. 조작과 규칙은 [HOWTOPLAY.txt](../HOWTOPLAY.txt)에 있습니다.
- 자동 플레이 스크립트와 시뮬레이션 스크립트는 테스트용 임시 사본(내부 상태를 읽도록 한 줄 추가한 게임)으로 돌렸고, 저장소에는 넣지 않았습니다.
